### What is SaaS?

Software as a Service (SaaS) is a software delivery model in which customers use an application through the internet, usually through a subscription.

Examples include Slack, Google Workspace and Salesforce.

### What is multi-tenancy?

Multi-tenancy means multiple customers share the same application infrastructure while their data and access remain logically separated.

For example:

- School A has its own students.
- School B has its own students.
- Both schools use the same application.
- School A must never access School B's data.

### How does it work?

A common approach is to use a shared database with a tenant identifier.

Example:

**students table**

| id | name | school_id |
|---|---|---|
| 1 | Rahim | 101 |
| 2 | Karim | 102 |
| 3 | Hasan | 101 |

When School A requests students, the backend applies:

```sql
SELECT *
FROM students
WHERE school_id = 101;
```

### Important concepts

- Tenant identification
- Tenant isolation
- Authentication
- Authorisation
- Database-level filtering
- Tenant-aware queries
- Data security

## 4.1 What is a payment gateway?

A payment gateway is a service that securely processes payment information and facilitates transactions between customers, merchants and financial institutions.

Examples:

- Stripe
- Paddle
- Xendit
- SSLCommerz

## 4.2 What is a unified payment processing layer?

Imagine your application supports Stripe, Paddle and Xendit.

Without a unified architecture, you might implement payment-specific logic throughout different parts of the application.

This creates duplication and makes maintenance difficult.

A unified processing layer provides a common interface.

Example:

```typescript
interface PaymentProvider {
  createPayment(data: PaymentData): Promise<PaymentResult>;

  verifyPayment(reference: string): Promise<PaymentResult>;

  refundPayment(reference: string): Promise<RefundResult>;
}
```

Different providers implement this interface.

```typescript
class StripeProvider implements PaymentProvider {
  async createPayment(data: PaymentData) {
    // Stripe-specific implementation
  }

  async verifyPayment(reference: string) {
    // Stripe-specific verification
  }

  async refundPayment(reference: string) {
    // Stripe-specific refund
  }
}
```

The application can use a common interface without depending on provider-specific implementation details.

**Why is this useful?**

1. Reduces code duplication.
2. Makes adding new payment providers easier.
3. Separates business logic from provider-specific logic.
4. Improves maintainability.
5. Simplifies testing.

## 4.3 What is a webhook?

A webhook is an HTTP callback through which one application notifies another application when an event occurs.

Example:

A customer pays through Stripe.

Stripe sends a notification to your backend:

```json
{
  "id": "evt_123",
  "type": "payment_intent.succeeded",
  "data": {
    "object": {
      "amount": 10000,
      "currency": "usd"
    }
  }
}
```

Your backend receives this event and updates the payment status.

### Payment workflow

1. Customer initiates payment.
2. Backend creates a payment request.
3. Payment provider processes the transaction.
4. Provider sends a webhook.
5. Backend verifies the webhook signature.
6. Backend checks whether the event has already been processed.
7. Backend updates the payment record.
8. Application activates the relevant service or subscription.

## 4.4 Why are webhooks important?

Payment processing is asynchronous.

The customer may close the browser before the payment provider finishes processing the transaction.

If you depend only on the frontend response, you may incorrectly assume that a payment failed even though the provider successfully processed it.

Webhooks provide server-to-server notifications.

## 4.5 What is webhook signature verification?

Payment providers usually sign webhook payloads using a secret key.

Your backend verifies the signature to ensure that the event genuinely came from the payment provider.

Without signature verification, an attacker might send a fake webhook claiming that a payment succeeded.

Example concept:

```typescript
const event = stripe.webhooks.constructEvent(
  rawBody,
  signature,
  webhookSecret
);
```

The exact implementation depends on the provider.

**Important:** Many payment providers require the original raw request body for signature verification.

## 4.6 What is idempotency?

Idempotency means processing the same operation multiple times produces the same final result as processing it once.

Why is this important?

Imagine Stripe sends the same successful payment webhook three times.

Without idempotency, your application might:

- Activate the subscription three times.
- Create duplicate records.
- Send duplicate notifications.
- Process duplicate business operations.

A common solution is to store the provider's event ID.

```sql
CREATE TABLE processed_webhooks (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    event_id VARCHAR(255) UNIQUE,
    processed_at TIMESTAMP
);
```

Before processing an event, check whether its event ID already exists.

Use a database transaction to ensure that event recording and business updates remain consistent.

## 4.7 What happens if webhook processing fails?

A reliable implementation should:

1. Verify the event.
2. Record the event safely.
3. Process it using transactional database operations.
4. Retry temporary failures.
5. Prevent duplicate processing.
6. Log errors for investigation.

For more complex systems, a background job queue can handle asynchronous processing.

## 4.8 What if the payment succeeds but the webhook never arrives?

The system should not depend exclusively on a single webhook delivery.

You can implement:

- Payment status reconciliation.
- Scheduled verification jobs.
- Provider API status checks.
- Retry mechanisms.
- Pending payment states.

For example, a scheduled job can identify payments that remain pending unusually long and verify their status with the provider.

# PART 5: Database Engineering and MySQL

Your CV says:

"Improved MySQL query response times by 10 to 30 percent on the highest-traffic endpoints through schema redesign, composite indexing, query pattern optimization, and critical query rewrites."

You should understand the following topics.

## 5.1 What is database indexing?

An index is a data structure that helps a database locate records more efficiently.

Without an index, MySQL may need to scan many rows to find the requested records.

Example:

```sql
SELECT *
FROM students
WHERE school_id = 101;
```

If `school_id` is not indexed, MySQL might perform a full table scan.

You can create an index:

```sql
CREATE INDEX idx_students_school
ON students(school_id);
```

### Advantages

- Faster SELECT queries.
- Better filtering performance.
- More efficient joins.
- Faster sorting in suitable cases.

### Disadvantages

- Requires additional storage.
- Slows down some INSERT, UPDATE and DELETE operations.
- Requires maintenance.

## 5.2 What is a composite index?

A composite index contains multiple columns.

Example:

```sql
CREATE INDEX idx_school_status
ON students(school_id, status);
```

This can help queries such as:

```sql
SELECT *
FROM students
WHERE school_id = 101
AND status = 'active';
```

### What is the leftmost prefix rule?

For an index on:

```sql
(school_id, status, created_at)
```

The index can generally support queries filtering by:

- `school_id`
- `school_id, status`
- `school_id, status, created_at`

But it generally cannot efficiently use the entire composite index for a query filtering only by `status`.

## 5.3 How do you identify slow queries?

Use:

```sql
EXPLAIN
SELECT *
FROM students
WHERE school_id = 101;
```

For MySQL versions that support it:

```sql
EXPLAIN ANALYZE
SELECT *
FROM students
WHERE school_id = 101;
```

Inspect:

- Access type.
- Possible keys.
- Selected key.
- Estimated rows.
- Actual execution time.
- Join strategy.

You can also investigate slow query logs.

## 5.4 What is a full table scan?

A full table scan means the database examines all rows in a table to find matching records.

It can be acceptable for small tables but expensive for large tables.

## 5.5 What is the N+1 query problem?

Suppose you fetch 100 courses and then execute a separate query for each course's instructor.

You execute:

- One query to fetch courses.
- 100 additional queries to fetch instructors.

Total: 101 queries.

This is the N+1 problem.

### Solution

Use JOINs or eager loading.

```sql
SELECT
    courses.id,
    courses.title,
    instructors.name
FROM courses
JOIN instructors
ON instructors.id = courses.instructor_id;
```

## 5.6 What is database normalisation?

Normalisation organises database tables to reduce unnecessary duplication and improve data integrity.

Common normal forms:

- 1NF: Atomic values and no repeating groups.
- 2NF: No partial dependency on a candidate key.
- 3NF: No inappropriate transitive dependency on a candidate key.

Example:

Instead of repeatedly storing department information in every employee row, store departments in a separate table and reference them using a foreign key.

## 5.7 What is denormalisation?

Denormalisation intentionally introduces some redundancy to improve read performance or simplify data access.

It can be useful for read-heavy applications, but it introduces additional consistency requirements.

## 5.8 What is database connection pooling?

Connection pooling maintains a reusable collection of database connections.

Instead of opening a new connection for every request, the application borrows an available connection and returns it when finished.

Benefits:

- Reduced connection overhead.
- Better resource utilisation.
- Improved performance under concurrent load.

## 5.9 How do you optimise a slow API?

Recommended approach:

1. Measure the response time.
2. Identify the slow operation.
3. Inspect SQL queries.
4. Check indexes.
5. Examine JOIN operations.
6. Avoid unnecessary data retrieval.
7. Reduce N+1 queries.
8. Consider caching where appropriate.
9. Measure again after optimisation.

### Interview answer

"I usually start by identifying the slowest part of the request rather than making random changes. I inspect the database queries, execution plans, indexes and data retrieval patterns. Then I optimise the query or schema and compare the response time before and after the changes."

# PART 6: Database Transactions and ACID

Your CV explicitly mentions atomic SQL transactions in critical payment and enrollment flows.

## 6.1 What is a database transaction?

A transaction is a group of database operations treated as a single logical unit.

For example, when a student enrolls in a course:

1. Create an enrollment record.
2. Record the payment.
3. Update the payment status.
4. Update the relevant business records.

These operations should remain consistent.

If one critical operation fails, the transaction can be rolled back.

Example:

```sql
START TRANSACTION;

INSERT INTO enrollments (student_id, course_id)
VALUES (101, 201);

UPDATE payments
SET status = 'completed'
WHERE id = 501;

COMMIT;
```

If an error occurs:

```sql
ROLLBACK;
```

In a real application, the transaction should also validate affected rows and handle exceptions.

## 6.2 What is ACID?

| Property | Meaning |
|---|---|
| Atomicity | All operations succeed or the transaction is rolled back |
| Consistency | Database rules remain valid |
| Isolation | Concurrent transactions do not improperly interfere |
| Durability | Committed changes survive failures according to database guarantees |

### Example

Suppose a banking application transfers $100 from Account A to Account B.

The application must:

- Deduct $100 from Account A.
- Add $100 to Account B.

If the deduction succeeds but the deposit fails, the transaction must not leave the system inconsistent.

## 6.3 What are transaction isolation levels?

MySQL InnoDB supports:

1. READ UNCOMMITTED
2. READ COMMITTED
3. REPEATABLE READ
4. SERIALIZABLE

### Dirty read

Reading uncommitted data from another transaction.

### Non-repeatable read

Reading the same row twice and receiving different committed values.

### Phantom read

Repeating a range query and seeing additional or missing rows because another transaction changed matching records.

### Interview question: What is the default isolation level in MySQL InnoDB?

REPEATABLE READ.

# PART 7: Authentication and RBAC

Your CV says you led a platform-wide RBAC rollout.

## 7.1 Authentication vs Authorisation

**Authentication:** Determines who the user is.

Example: Logging in with email and password.

**Authorisation:** Determines what the authenticated user is allowed to do.

Example: A teacher can manage courses but cannot manage system administrators.

## 7.2 What is RBAC?

Role-Based Access Control assigns permissions to roles, and users receive permissions through those roles.

Example:

| Role | Permissions |
|---|---|
| Admin | Manage users, courses and settings |
| Teacher | Manage assigned courses |
| Student | View enrolled courses |
| Moderator | Manage reviews |

## 7.3 How does RBAC work?

A common database design:

**users**

```text
id
name
email
```

**roles**

```text
id
name
```

**permissions**

```text
id
name
```

**user_roles**

```text
user_id
role_id
```

**role_permissions**

```text
role_id
permission_id
```

When a user requests a protected resource:

1. Authenticate the user.
2. Retrieve their role or roles.
3. Identify the required permission.
4. Check whether the user has that permission.
5. Allow or reject the request.

## 7.4 Why centralised permission management?

Without centralisation, developers might implement permission checks separately in multiple controllers.

This causes:

- Duplicated logic.
- Inconsistent access rules.
- Difficult maintenance.
- Security mistakes.

A centralised policy layer makes permissions easier to maintain and audit.

## 7.5 What is JWT?

JSON Web Token (JWT) is a compact token format used to transmit claims between parties.

A JWT generally consists of three parts:

```text
Header.Payload.Signature
```

### Header

Contains token metadata, including the signing algorithm.

### Payload

Contains claims such as user ID and expiration time.

### Signature

Used to verify token integrity and authenticity.

Important: JWT payloads are encoded, not automatically encrypted.

## 7.6 Access token vs Refresh token

| Access token | Refresh token |
|---|---|
| Used to access protected resources | Used to obtain new access tokens |
| Usually short-lived | Usually longer-lived |
| Sent with API requests | Used at the token refresh endpoint |

Security considerations include secure storage, expiration, rotation and revocation strategies.

# PART 8: Node.js and Backend Engineering

Your strongest technical area is backend engineering. Prepare these questions carefully.

## 8.1 What is Node.js?

Node.js is a JavaScript runtime built on the V8 JavaScript engine. It allows JavaScript to run outside the browser.

It is widely used for:

- REST APIs.
- Real-time applications.
- Microservices.
- Background processing.
- Network applications.

## 8.2 Is Node.js single-threaded?

JavaScript execution in the main event loop is generally single-threaded.

However, Node.js uses additional mechanisms, including:

- The event loop.
- Operating system asynchronous I/O.
- The libuv thread pool.
- Worker threads.

Therefore, saying "Node.js is completely single-threaded" is inaccurate.

## 8.3 Explain the event loop.

The event loop allows Node.js to handle asynchronous operations without blocking JavaScript execution while waiting for I/O.

Example:

```javascript
console.log("Start");

setTimeout(() => {
  console.log("Timer");
}, 0);

console.log("End");
```

Output:

```text
Start
End
Timer
```

The timer callback executes later, after the current synchronous code has completed.

## 8.4 What is non-blocking I/O?

Non-blocking I/O means the application can initiate an I/O operation and continue executing other work instead of waiting synchronously for the operation to finish.

For example, while waiting for a database response, Node.js can process other requests.

## 8.5 What is middleware?

Middleware is a function that executes during the request-response lifecycle.

Typical responsibilities:

- Authentication.
- Logging.
- Request validation.
- Error handling.
- Authorisation.
- Rate limiting.

Example:

```javascript
function logger(req, res, next) {
  console.log(req.method, req.url);
  next();
}
```

## 8.6 What is REST API?

REST is an architectural style for designing networked APIs around resources.

Common HTTP methods:

| Method | Purpose |
|---|---|
| GET | Retrieve resources |
| POST | Create resources or trigger processing |
| PUT | Replace a resource |
| PATCH | Partially update a resource |
| DELETE | Delete a resource |

Common HTTP status codes:

| Code | Meaning |
|---|---|
| 200 | OK |
| 201 | Created |
| 204 | No Content |
| 400 | Bad Request |
| 401 | Unauthenticated |
| 403 | Forbidden |
| 404 | Not Found |
| 409 | Conflict |
| 422 | Unprocessable Content |
| 429 | Too Many Requests |
| 500 | Internal Server Error |
| 503 | Service Unavailable |

## 8.7 PUT vs PATCH

PUT generally replaces the complete representation of a resource.

PATCH applies partial modifications.

## 8.8 What is dependency injection?

Dependency injection means providing a component with its dependencies instead of making it create those dependencies internally.

Benefits:

- Loose coupling.
- Better testability.
- Easier maintenance.
- Flexible implementations.

## 8.9 What is SOLID?

| Principle | Meaning |
|---|---|
| S – Single Responsibility | A class should have one main responsibility |
| O – Open/Closed | Open for extension, closed for modification |
| L – Liskov Substitution | Subtypes should be usable wherever their base types are expected |
| I – Interface Segregation | Prefer focused interfaces over large general-purpose ones |
| D – Dependency Inversion | High-level modules should depend on abstractions |

### Example: Single Responsibility Principle

A payment service should not also be responsible for sending marketing emails, generating PDF reports and managing user authentication.

Separate responsibilities make code easier to test and maintain.

## 8.10 What is caching?

Caching stores frequently accessed data so that subsequent requests can retrieve it more quickly.

Redis is commonly used for caching.

Example:

```javascript
const cached = await redis.get("user:101");

if (cached) {
  return JSON.parse(cached);
}

const user = await db.user.findUnique({
  where: { id: 101 }
});

await redis.set(
  "user:101",
  JSON.stringify(user),
  "EX",
  300
);

return user;
```

The exact Redis client syntax varies.

### Cache invalidation

Cache invalidation means removing or updating cached data when the underlying source changes.

A common challenge is stale data.

# PART 9: Your Real-Time Chat Achievement

Your CV says:

## 9.1 What is real-time communication?

Real-time communication allows information to be exchanged with minimal delay.

Examples:

- Chat applications.
- Live notifications.
- Multiplayer games.
- Collaborative editing.

## 9.2 What is WebSocket?

WebSocket is a communication protocol that provides a persistent, bidirectional connection between a client and a server.

Unlike ordinary HTTP request-response communication, WebSocket allows either side to send messages independently after establishing the connection.

## 9.3 WebSocket vs HTTP

| HTTP | WebSocket |
|---|---|
| Request-response model | Bidirectional communication |
| Usually separate requests | Persistent connection |
| Suitable for conventional APIs | Suitable for real-time communication |

## 9.4 What is connection pooling?

Connection pooling reuses available connections instead of creating new ones for every operation.

It reduces resource overhead and improves efficiency.

## 9.5 What is message batching?

Message batching means grouping multiple messages or operations together before processing or transmitting them.

For example, instead of processing every small operation individually, a system can group suitable operations into a batch.

Potential benefits:

- Fewer database operations.
- Reduced overhead.
- Better throughput.

However, batching must balance throughput against message latency.

## 9.6 What is concurrency?

Concurrency means multiple tasks make progress during overlapping periods.

A system supporting thousands of simultaneous users must manage connections, memory, database access and message delivery efficiently.

# PART 12: Important Technical Differences

These are common questions in primary software engineering interviews.

| Question | Short answer |
|---|---|
| SQL vs NoSQL | SQL databases generally use relational structures; NoSQL databases use different data models |
| MySQL vs PostgreSQL | Both are relational databases with different capabilities and ecosystems |
| MongoDB vs MySQL | MongoDB uses document storage; MySQL uses relational tables |
| Redis vs MySQL | Redis is an in-memory data store; MySQL is a relational database |
| REST vs GraphQL | REST uses resource-oriented endpoints; GraphQL allows clients to request specific data through a query language |
| Monolith vs Microservices | Monolith deploys an application as a unit; microservices split functionality into independently deployable services |
| Authentication vs Authorisation | Identity verification vs permission checking |
| Horizontal vs Vertical scaling | Adding more machines vs increasing the capacity of an existing machine |
| Synchronous vs Asynchronous | Waiting for an operation to complete vs allowing other work to proceed |
| Process vs Thread | A process is an executing program; a thread is an execution unit within a process |
| Encryption vs Hashing | Encryption is reversible with the appropriate key; hashing is designed to be one-way |
| Queue vs Stack | FIFO vs LIFO |
| INNER JOIN vs LEFT JOIN | Matching rows only vs all left-table rows and matching right-table rows |
| DELETE vs TRUNCATE | Deletes selected rows vs removes all rows from a table |
| Primary key vs Foreign key | Uniquely identifies a row vs references a key in another table |

# PART 13: JavaScript and TypeScript Questions

## 13.1 var vs let vs const

| Feature | var | let | const |
|---|---|---|---|
| Scope | Function | Block | Block |
| Reassignment | Yes | Yes | No |
| Redeclaration in same scope | Yes | No | No |

Prefer `const` by default and use `let` when reassignment is necessary.

## 13.2 == vs ===

`==` performs type coercion where applicable.

`===` compares values without automatic type coercion.

```javascript
5 == "5"  // true
5 === "5" // false
```

## 13.3 Promise vs async/await

A Promise represents the eventual completion or failure of an asynchronous operation.

`async/await` provides a cleaner syntax for working with Promises.

```javascript
async function getUser() {
  try {
    const response = await fetch("/api/users/1");
    return await response.json();
  } catch (error) {
    console.error(error);
  }
}
```

## 13.4 What is closure?

A closure occurs when a function retains access to variables from its lexical scope, even after the outer function has finished executing.

```javascript
function counter() {
  let count = 0;

  return function () {
    count++;
    return count;
  };
}

const increment = counter();

increment(); // 1
increment(); // 2
```

## 13.5 What is TypeScript?

TypeScript is a strongly typed programming language built on JavaScript that adds static type checking.

Benefits:

- Better code maintainability.
- Improved developer experience.
- Early error detection.
- Better IDE support.
- Safer refactoring.

## 13.6 Interface vs Type in TypeScript

Both describe types, but they have different capabilities.

Interfaces are commonly used to describe object contracts and can be extended or declaration-merged.

Type aliases can represent unions, intersections, primitives, tuples and other types.
